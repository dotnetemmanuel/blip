# blip ui Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
>
> This plan deliberately carries no code listings. Each step names the file, the
> behavior, and what its test must prove. The implementer writes the code.

**Goal:** Add `blip ui`, an interactive terminal explorer that discovers the
current repo's API on its own, browses it Scalar-style, sends requests, and
leaves the working directory untouched.

**Architecture:** Three phases that stack. A shared theme module extracted from
Cairn so blip, Cairn and jotter stop drifting. A discovery package that answers
"what API lives here" from manifests, run profiles and listening sockets, with
no UI attached and no network in its tests. Then the bubbletea UI, which is a
new face on blip's existing spec, auth and request machinery.

**Tech Stack:** Go 1.26, cobra, kin-openapi, bubbletea, bubbles, lipgloss,
chroma (response and snippet highlighting), glamour (markdown descriptions),
atotto/clipboard.

**Spec:** `docs/superpowers/specs/2026-08-04-blip-ui-design.md`

## Global Constraints

Every task inherits these. They come from blip's `CLAUDE.md` and the spec.

- `make lint test build` passes before any task is proposed as done.
- **stdout carries only the response body.** `ui` refuses to start when stdout
  is not a terminal. Nothing in the UI writes to stdout.
- **Credentials resolve lazily.** Launching and browsing must not reach for a
  vault. Only the first send resolves.
- **`readonly` is not overridable.** Not by any key, not by any confirm.
- **Exit codes are a contract** (`internal/output/exit.go`). Errors carry codes
  by wrapping with `output.WithCode`, never by top-level inspection.
- **A schema type is a set, not a value.** Use `schemaType`, never
  `Types.Is()`. OpenAPI 3.1 writes `"type": ["integer", "string"]`.
- **A path argument may not climb.** A `..` segment is refused, not encoded.
- **A tag is not always a group.** Reuse `build`'s tag logic, including
  discarding .NET's assembly-name tag.
- **Secrets redact by value** through `internal/output.Redactor`. Matching is
  literal, so a re-encoded secret escapes it.
- **Existing golden files do not change.** `make golden` only for new ones.
- **No test touches the network.** `httptest.Server` throughout.
- **The UI references semantic theme roles only, never a hex literal.**
- No em dashes in any output, comment, doc or commit message.

### Task 3: Theme resolution, modes and per-token override

**Files:**
- Create: `~/Source/GitHub/termtheme/theme.go`
- Create: `~/Source/GitHub/termtheme/theme_test.go`

**Interfaces:**
- Consumes: `Palette`, `Resolved()` from Task 1; `NamedTheme` from Task 2.
- Produces, matching Cairn's existing API exactly so Cairn migrates by changing
  an import: `Theme` (the same token set as `Palette` but typed
  `lipgloss.Color`); constants `ModeDark` and `ModeLight`;
  `Toggle(mode string) string`; `Resolve(mode string, override Palette) Theme`;
  `ResolveNamed(nt NamedTheme, mode string, override Palette) Theme`.

**Why two types.** `Palette` is hex strings and is what JSON and config carry.
`Theme` is `lipgloss.Color` and is what the UI holds. Keeping them separate is
what lets the UI reference semantic roles only and never a hex literal.

**The override** is a partial `Palette` from user config layered over the named
theme, token by token, before resolution. The settings preview carries it too,
so what you preview is what you get.

- [x] **Step 1: Write the failing tests**

  `Toggle` flips dark to light and light to dark, and collapses any unrecognised
  value to dark. `ResolveNamed` with `ModeLight` returns the light variant.
  An override setting only `Primary` changes `Primary` and leaves every other
  token from the named theme intact. An override is applied before fallbacks, so
  overriding `Danger` on a theme with no `Error` also moves `Error`.

  That last case is the one worth being careful about: it is the difference
  between an override that behaves like the theme file and one that does not.

- [x] **Step 2: Run them and confirm they fail**

- [x] **Step 3: Implement resolution**

  Port Cairn's `theme.Resolve` and `ResolveNamed`. Order is: named theme variant,
  then override layered on top, then `Resolved()` fallbacks, then conversion to
  `lipgloss.Color`.

- [x] **Step 4: Run the tests and confirm they pass**

- [x] **Step 5: Commit and tag**

  `feat: resolve a named theme and mode into lipgloss colors`, then
  `git tag v0.1.0` so blip requires a fixed version rather than a
  pseudo-version.

### Task 7: The discovery ladder

**Files:**
- Create: `internal/detect/discover.go`
- Create: `internal/detect/discover_test.go`

**Interfaces:**
- Consumes: `DetectFrameworks`, `ReadRunProfile`, `ListenersUnder` from Tasks 4
  to 6; `config.LoadFrom`, `spec.Fetcher`, `spec.ProbePaths` from blip.
- Produces: `Target{Title, BaseURL, SpecURL string; Env *config.Environment; Framework *Framework}`;
  `Ledger{Attempts []Attempt}` where `Attempt{Rung, Detail, Outcome string}`;
  `Discover(ctx, repoRoot string, client *http.Client) ([]Target, Ledger, error)`.

**The ladder, in order, stopping at the first rung that yields a document.**

1. `.blip.toml` via `config.LoadFrom`. A written-down answer beats a discovered
   one, so this is first. When present, every rung below is skipped.
2. A spec file on disk: `openapi.{json,yaml,yml}`, `swagger.{json,yaml,yml}`,
   under the repo root, `api/`, `docs/` or `spec/`.
3. Frameworks and run profiles, producing a candidate base URL and spec path
   per project. This is a guess, not a document.
4. Probe. Take each guess and try its spec paths in order. With no guess, probe
   every listener from Task 6 against the full path set. Accept a self-signed
   certificate on loopback only.

**Why rung 4 is the common path.** `Microsoft.AspNetCore.OpenApi`, FastAPI,
NestJS and springdoc all build the document in memory at boot and serve it over
HTTP. Nothing reaches disk. Smarticipate has no spec file, only DLLs.

**The probe path order differs from blip's.** blip's runtime `ProbePaths` is
four .NET-leaning paths because `init` already wrote the answer down. `ui` has
no config to consult, so it probes the union of `spec.ProbePaths` and
`cli.extraProbePaths`, ordered by whatever rung 3 suggested. Promote
`extraProbePaths` out of `internal/cli` into `internal/spec` so both can reach
it, leaving blip's own runtime behavior unchanged.

**The ledger.** Every rung records what it tried and what it concluded, whether
or not discovery succeeds. This is what turns "no API found" into a sentence
that tells you what to do next, and it is why the ledger is returned even on
success.

- [x] **Step 1: Write the failing tests**

  These mirror the manual matrix in Task 19, so every row is covered twice: once
  against fixtures here, once against real services there. Where a row is
  reachable from a fixture, it belongs here too.

  Rung 1 wins: a fixture with both a `.blip.toml` and a spec file yields the
  config's target and the ledger shows the spec file was never consulted.
  Rung 1 walking up: discovery started from a subdirectory finds the config
  above it.
  Rung 2: a fixture with only a spec file yields a target with no network call
  (assert with an `http.Client` whose transport fails the test if used).
  Rung 4 hit: an ASP.NET fixture plus an `httptest.Server` serving
  `/openapi/v1.json` yields one target, and the ledger names the port it came
  from.
  Rung 4, port answers but no spec: the server returns 404 for every probe path,
  and the ledger says the port was reached and served no spec. This is the
  `IsDevelopment` gate, and it is the failure most likely to be misreported as
  "nothing is running".
  Rung 4, wrong guess recovered: the run profile advertises one port, the fake
  socket source reports the service on another, and discovery finds it anyway.
  Probe order follows detection: a FastAPI fixture tries `/openapi.json` before
  `/openapi/v1.json`, and an ASP.NET fixture does the reverse. Assert on the
  request order the test server saw.
  Foreign process excluded: a fake socket source reports a listener whose cwd is
  outside the repo, and it is not probed at all.
  Certificate rule: a self-signed certificate is accepted for a loopback host
  and refused for a non-loopback one, with the reason in the ledger.
  Total failure: a fixture with nothing yields no targets, no error, and a
  ledger with four attempts each carrying a non-empty outcome.
  No false positive: a fixture holding only a bundler `package.json` yields no
  targets and no start offer.
  Monorepo: a fixture with two projects yields two targets.

- [x] **Step 2: Run them and confirm they fail**

- [x] **Step 3: Move `extraProbePaths` into `internal/spec`**

  Export it as `spec.ExtraProbePaths` and have `internal/cli/init.go` reference
  the moved value. Confirm blip's existing tests and goldens still pass, since
  this touches shipped behavior.

- [x] **Step 4: Implement `Discover`**

- [x] **Step 5: Run the full suite and confirm it passes**

  `make lint test`. The existing golden files must be untouched.

  `feat: discover a repo API from config, files, manifests and open ports`

### Task 8: Refuse Swagger 2.0 out loud

**Files:**
- Modify: `internal/build/parse.go`
- Modify: `internal/build/parse_test.go`
- Create: `testdata/swagger20-petstore.json`

**Interfaces:**
- Consumes: nothing new.
- Produces: no signature change. `Parse` gains an early refusal.

**The defect.** `spec.looksLikeSpec` accepts a document carrying either an
`openapi` or a `swagger` key, but `build.Parse` loads with `openapi3.NewLoader`,

accepted as spec-shaped and parsed into operations with no usable parameter or
body information, silently. Older Java and Node services still serve 2.0.

This is a live blip bug, not a UI concern, which is why it is fixed here in the
shared layer rather than in the UI.

- [x] **Step 1: Add the fixture**

  `produces`. The classic Petstore 2.0 is fine.

- [x] **Step 2: Write the failing test**

  Assert `Parse` on the 2.0 fixture returns an error naming the version and
  saying only OpenAPI 3.x is supported, and that the error carries the config
  exit code. Assert the existing 3.0 and 3.1 fixtures still parse unchanged.

- [x] **Step 3: Run it and confirm it fails**

  It will currently return operations and no error, which is the bug.

- [x] **Step 4: Implement the refusal**

### Task 11b: Wire the panes into a screen you can actually use

Added after Task 11, at the human's direction. It is numbered `11b` rather than
renumbering 12 to 19, because the ledger, the review packages and the
`task-brief` script all address tasks by number and renumbering would invalidate
every existing reference.

**Why this exists:** Tasks 10 and 11 built `listModel` and `detailModel`, and
neither is constructed anywhere outside its own tests. The root model still only
knows about discovery, so none of the list, search, group hopping, markdown
descriptions or response shapes can be reached by running the binary. No task in
this plan composed them, and none of Tasks 12 to 17 would have either. Without
this task the Fill and Send states are also built blind, and every integration
defect surfaces at once in Task 19.

**Files:**
- Modify: `internal/ui/app.go` (root model gains the panes and the states)
- Modify: `internal/cli/ui.go` (bind the loader)
- Create: `internal/ui/screen.go` (layout and the state machine, if `app.go`
  would otherwise grow past one clear responsibility)
- Create: `internal/ui/screen_test.go`

**Interfaces:**
- Consumes: `listModel` (Task 10), `detailModel` (Task 11), `detect.Target` and
  `detect.Ledger` (Task 7), `build.Parse`.
- Produces: `Options.LoadAPI`, and a root `Model` that moves between
  discovering, choosing a target, browsing, and failed.

**How the spec is loaded, and why it is injected.** Discovery does not hand back
a parsed API. Rung 1, the `.blip.toml` case and the most common one, records
`SpecURL` from config without ever fetching it (`configTarget` in
`internal/detect/discover.go`). So the screen has to load the document itself.

### Task 11c: Carry nullability, because required and nullable are different

Added at the human's direction after seeing the Read pane, and numbered `11c`
for the same reason `11b` was: the ledger and `task-brief` address tasks by
number.

**Why this exists:** `schemaType` deliberately drops `"null"` from a 3.1 type
union (`internal/build/parse.go:400`), which is correct for its job of deciding
what a flag binds to, since nobody types null at a prompt. But nothing records
that the value was nullable, so the information is gone before anything renders.
The sandbox spec really carries these: `CreateOrderRequest.note` and
`Order.tenant` are both `["null", "string"]`, and both display today as a plain
`string`, indistinguishable from a field that must hold a value.

Required and nullable are orthogonal, and all four combinations are real: an
optional field that may be null, a required field that must be present but may
be null, and the two non-nullable cases. blip can currently express only the
non-nullable column.

**This is a prerequisite for Task 12, not a display nicety.** The Fill state
validates before sending. Without nullability it cannot tell "this required
field needs a value" from "this required field must be present but may be null",
so it would reject a legitimate null.

**Files:**
- Modify: `internal/build/model.go` (`Param` and `Field` gain `Nullable`)
- Modify: `internal/build/parse.go` (detect both spellings)
- Modify: `internal/ui/detail.go` (render it)
- Modify: the corresponding test files

**Both spellings must work**, because the fixtures cover both. OpenAPI 3.1, which
`dotnet10-minimal.json` is, writes `"type": ["null", "string"]`. OpenAPI 3.0,
which `dotnet9-minimal.json` is, writes a separate `nullable: true`.

**Do not change what `describe` prints.** The `describe --compact` and
`--dry-run` goldens are contracts an agent parses, and whether that surface
should also carry nullability is a separate question for the human. This task is
the parsed model plus the UI only.

- [x] **Step 1: Write the failing tests**

  A 3.1 parameter typed `["null", "string"]` is nullable and still binds as a
  string. A 3.0 parameter carrying `nullable: true` is nullable. A plain
  parameter is not. The same three for a body field. Required and nullable are
  independent: assert a required non-nullable, an optional nullable and a
  required nullable all render distinguishably, in one render, since a test that
  checks only the marker's presence passes whichever way the two are conflated.

- [x] **Step 2: Run them and confirm they fail**

- [x] **Step 3: Implement it**

  Set `Nullable` where the type set is already being read, rather than walking
  the schema a second time.

- [x] **Step 4: Run the tests and confirm they pass**

- [x] **Step 5: Commit**

  `feat: carry nullability through the model and show it beside required`

## Self-review notes

**Spec coverage.** Every section of the design has a task. Discovery rungs 1 to
4 are Tasks 4 to 7. The three pane states are Tasks 11 to 13. Auth is Task 14,
snippets Task 15, theme and keys Task 16, failure and the start fallback Task 17.
The `error` token is decided in Task 2 and proven in Task 13. The Swagger 2.0
refusal is Task 8.

**Two things the plan adds that the spec left implicit.** Killing the child
process on quit (Task 17), because an orphaned dev server violates the
leaves-nothing-behind promise. And Task 12's assertion that `formModel.Resolve`
produces the same request as blip's `send` for the same inputs, which is the
only mechanical guard against the UI and the CLI drifting apart.

**One decision made here rather than in the spec.** Task 2 resolves the
retro-82 light disagreement in jotter's favour, keeping `text` at `#24404f` and
`line` at `#0a2138`, on the reasoning that Cairn's single value was that split
collapsed into one token. Worth a glance before Phase 1 starts, since it changes
how Cairn looks once it migrates.

**Theme parity.** Phase 1 mirrors Cairn's API deliberately (`Palette` versus
`Theme`, `Resolve`, `ResolveNamed`, `Toggle`, the mode constants, the override
layer) so Cairn migrates onto the shared module by changing an import rather
than by rewriting. Task 16 ports Cairn's `settingsModel` behaviour for
behaviour rather than building a new picker, including the live full-box
repaint and the four-part preview.

**No database anywhere.** `blip ui` stores nothing and depends on no service.
The sandbox in Task 18 is deliberately free of databases, brokers and containers
so it tests blip's plumbing rather than someone else's. The one place a database
shows up is Task 17: a started project may need one, and its failure has to
surface the child's own output.

**Ordering.** Phases are strictly sequential. Within Phase 2, Tasks 4 to 6 are
independent of each other and could run in parallel; Task 7 needs all three.
Within Phase 3, Tasks 10 to 17 each depend on Task 9 and then mostly on their
predecessor, since they share `ui.Model`. Task 18 has no dependencies and could
be built at any point, including first.
